# 案例检索与归档技能

## 触发场景

当用户要求查案例、类案检索、裁判观点、案例表、案例链接、法宝链接、全文归档，或需要用案例支撑法律咨询结论时，使用本技能。

本技能可以配合：

- `china-regulatory-consulting`：生成法规咨询和客户可发文稿。
- `web-access`：检索微信公众号、法答网、法院公号、一线律所文章等实务观点，再倒查其引用案例。
- `wechat-article-archive-codex`：用户要求归档微信公众号文章全文时使用。

## 总原则

1. 先查本地归档，再做新检索。
2. 案例表以原文摘录为核心，避免只写概括性结论。
3. 每个引用案例必须保存完整 JSON；只有完整裁判全文写入 JSON 后，才可视为已归档。
4. 法宝、华语原典、法院官网等检索工具返回的摘要、片段、字段型结果，只能作为线索；不能替代全文归档。法宝语义检索只返回片段时，应沿案例链接进入详情页，优先使用下载按钮导出 txt 或可复制全文，再补成完整 JSON。
5. 实务文章是线索和观点参照，也必须留痕。正式引用案例前，必须倒查案例原始数据库或法院来源，并保存全文 JSON；检索到、采用或排除的重要文章链接、核心观点摘要、引用法规/规则摘要应进入源素材记录或案例表对应字段，便于用户复核。

## 案例归档位置

每个案例只保存到当前事项本地归档：

- `<当前工作事项最底层文件夹>/case-json/YYYY-MM-DD_事项名/`
- “最底层文件夹”指本次交付文件所在的具体工作目录，不默认放入某个客户 wiki。
- 不再向中央库复制案例 JSON；司法案例全文 JSON 体量较大，按事项归档即可。跨事项复用时，由用户指定旧项目或旧成果后再检索对应目录。

文件名建议：

`案号_法院_简短案名.json`

文件名中不得使用 `/`、`:` 等路径特殊字符；当事人较长或匿名时，使用可识别简称。

## 开始前先查归档

新检索前，先用 `rg` 检查：

1. 当前事项 `case-json/`；
2. 如用户指定旧项目或旧成果，再查对应项目中的 `case-json/`、案例表、研究稿。

可检索关键词包括：案号、法院、当事人简称、争议类型、裁判观点关键词、法规条号、用户问题关键词。

若归档 JSON 已存在且 `full_text_status` 为 `complete`，优先复用；若为 `partial`、`snippet_only` 或缺少全文，需要重新获取全文后覆盖或另存新版。法宝链接补全文的具体流程见 `references/pkulaw-fulltext-txt.md`。

## 检索路径

### 路径一：法律数据库直接检索

1. 使用可调用的法律 MCP 或数据库工具检索案例。
2. 按案号、法院、裁判日期、争议焦点、裁判理由初筛。
3. 打开详情页或调用详情接口取得完整裁判全文；法宝语义检索未给全文时，沿返回链接进入详情页，通过下载按钮选择 txt 导出，或用浏览器复制全文。
4. 保存完整 JSON 到当前事项本地归档。
5. 从完整全文中摘录“本院认为”等关键段落，形成案例表。

### 路径二：实务观点倒查案例

适用于关键词不稳定、裁判观点较新、或数据库检索难以命中的问题。

1. 使用 `web-access` 获取实务观点文章。微信公众号、法答网、法院公号等生态优先通过 `web-access`/真实浏览器路径进入。
2. 先按权威来源优先级组织检索：法答网优先，其次最高人民法院、人民法院报/中国法院网、各级法院官方公众号和公开文章，再到高质量律所/争议解决团队文章。具体分层见 `references/practical-source-priority.md`。
3. 提取文章中的观点、案号、当事人、法院、裁判日期、引用规则、文章标题、发布主体、发布日期和 URL；源素材记录必须写明文章核心观点摘要和相关法规/裁判规则摘要，不能只写“规则背景”。
4. 将文章保存为线索记录；如用户要求归档微信公众号文章全文，配合 `wechat-article-archive-codex`。
5. 案例表或源素材表必须保留采用文章的链接；重要但最终未采用的文章，也应在源素材记录中说明排除原因，便于用户复核。
6. 根据线索倒查法律数据库或法院来源。
7. 只有倒查取得完整裁判全文并保存 JSON 后，才可在正式法律意见中引用该案例。

## 类案筛选顺序

参照《最高人民法院关于统一法律适用加强类案检索的指导意见（试行）》进行检索组织。优先考虑：

1. 最高人民法院发布的指导性案例；
2. 最高人民法院发布的典型案例及裁判生效案件；
3. 本省、自治区、直辖市高级人民法院发布的参考性案例及裁判生效案件；
4. 上一级人民法院及本院裁判生效案件；
5. 其他法院事实相似、争点相近、说理充分的裁判生效案件。

不要在案例表中设置“参考权重”字段。若使用外地基层或一审案例，只在正文中客观说明其层级、地域和事实相似性，不写成单独表格字段。

## JSON 完整性要求

保存前确认：

1. `full_text` 字段包含裁判文书全文，尤其包括当事人信息、诉讼请求、事实认定、本院认为、裁判结果。
2. 若工具输出因 token 限制被截断，不得把截断内容标记为完整全文；应通过详情页下载、分页抓取、导出、浏览器复制全文、PDF/OCR 等方式补齐。
3. 若确实无法取得全文，仍可保存线索 JSON，但必须标记：
   - `full_text_status: "partial"` 或 `"snippet_only"`；
   - `not_complete_reason`；
   - `next_retrieval_steps`。
4. 正式引用的案例原则上应为 `full_text_status: "complete"`。

JSON 字段模板见 `references/case-json-schema.md`。

## 案例表字段

常规案例表使用以下字段：

| 字段 | 写法 |
| --- | --- |
| 案例名称 | 使用数据库标题或裁判文书标题。 |
| 案号/法院/裁判日期 | 合并写明案号、审理法院、裁判日期。 |
| 法律关系与核心主张 | 简要写明各方关系、请求权基础、原被告或上诉人核心主张。 |
| 本院认为 | 摘录与拟证实裁判观点有关的法院原文；可用省略号删去无关内容，但不得改写成只有己方有利的总结。 |
| 裁判结果 | 简要写明支持、驳回、改判、维持、继续履行、违约金等结果。 |
| 案例链接 | 优先放北大法宝或其他可验证数据库链接；必要时附法院/裁判文书网链接。 |
| 线索文章/源素材链接 | 如案例由法答网、法院公号、微信公众号、律所文章等发现，列明文章标题、发布主体和 URL；没有则写“无”。 |

不得添加“参考权重”“对本问题的参考意义”“律师适用说明”等字段。案例支持什么、不支持什么、适用边界是什么，应在正文法律分析中表达，而不是写入案例表字段。

表格模板见 `references/output-table-template.md`。

## 本院认为摘录规则

1. 优先摘录原文段落，不只写一句总结。
2. 保留法院的限制条件、转折和事实基础。
3. 摘录前后可用简短引导语，但引导语不能替代原文。
4. 对用户不利或限制结论的内容，不得故意省略到改变裁判含义。
5. 若原文过长，可使用 `……`，但要保持句义完整。

## 交付前检查

交付前逐项确认：

1. 引用案例均有可验证链接。
2. 正式引用案例均已保存完整 JSON，或已明确标注未完整归档原因。
3. 当前事项本地归档已保存。
4. 案例表未包含用户要求删除的字段。
5. “本院认为”保留了足够原文，不是只写倾向性概括。
6. 如引用实务文章发现案例，已完成倒查并以案例原文为准。
7. 检索到并采用的实务文章、微信公众号文章、法答网问答、法院文章链接已进入案例表或源素材记录。

## Scripts

- `scripts/search_case_json.py`：检索当前事项或用户指定旧项目中的案例 JSON。
- `scripts/case_matter.py`：初始化事项内 `case-json/YYYY-MM-DD_事项名/` 目录，并可回填 JSON 完整性字段。
- `scripts/case_json_lint.py`：校验案例 JSON 完整性，不把摘要/片段误标为完整全文。
- `scripts/case_table_from_json.py`：从合格 JSON 生成含源素材链接的 Markdown 案例表。
- `scripts/pkulaw_txt_to_case_json.py`：把从法宝下载或复制的裁判文书 txt 合并进既有线索 JSON，回填全文、哈希和完整性字段。
