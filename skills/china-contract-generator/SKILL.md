# 中国合同生成

## 目标

从真实交易而非合同名称出发，形成法律关系准确、权利义务可履行、风险闭环完整、表达适合中国合同实践并符合客户立场的合同。

默认采用两阶段交付：

1. 先生成并保存`起草前提要.md`，供律师确认法律关系、依据和拟起草逻辑；
2. 律师确认后再起草合同，并交付`.docx`。不得把合同 Markdown 作为降级交付稿。

正文供双方签署，批注及起草前提要供客户或律师内部决策，三者不得混写。

## 一、先建立事实与办案上下文

按下列优先级读取，近端规则优先于通用模板：

1. 当前目录及上级目录中适用的 `AGENTS.md`；
2. 项目 wiki 的规则、索引、近期日志、原材料地图、客户画像及相关事项/合同类型/条款口径；
3. 客户邮件、需求说明、业务方案、报价单、流程图、附件和已确认问答；
4. 客户已定稿或律师认可的同类合同及 Word 格式；
5. 现行法律、监管规则、案例和官方解释；
6. 通用模板、外部 skill 和行业惯例。

不得用通用模板覆盖已确认的客户事实。区分“材料已确认”“合理推断”“必须确认”；不确定事项不得写成确定事实。

如客户提供了 Word 参考稿，应读取正文、修订、批注、样式、页眉页脚和附件结构，不得只抽取纯文本。

项目内没有更优先的定稿合同时，先读 [references/example-contracts.md](references/example-contracts.md)，再按交易类型选择性读取 [医疗产品采购及病例资料合作协议脱密示例](references/医疗产品采购及病例资料合作协议_脱密示例.docx) 或 [物料采购合同脱密示例](references/物料采购合同_脱密示例.docx)。示例只提供结构、措辞和风险闭环参考，不替代法律核验与客户事实确认。

## 二、先定法律关系，形成起草前提要

在起草合同正文前，必须形成并保存一份 Markdown 起草前提要，至少回答：

- 各方真实身份、资质、角色和所代表客户；
- 交易目的、核心标的及最终成果；
- 货物、服务、资金、票据、数据、知识产权/品牌分别如何流动；
- 谁决定、谁实施、谁验收、谁控制相应风险；
- 付款或其他对价与何项真实履行成果对应；
- 是否构成买卖、服务、委托、许可、租赁、投资、担保或混合合同；
- 是否叠加医疗、金融、数据、广告、劳动、建设工程等强监管属性；
- 正常履行、异常履行、解除后存量事项如何处理。

起草前提要还应包括：

- 已确认事实、作业假设和仍待确认事项；
- 法律关系定性及存在的备选定性；
- 主要法律依据、与本交易的对应关系、核验来源和核验状态；
- 拟采用的合同名称、章节结构及主要履行闭环；
- 核心权利义务、风险分配、批注和运营落实方案；
- 可能改变合同结构的选择项及各自影响。

文件名遵守项目规则；无规定时使用`{合同名称}_起草前提要_YYYYMMDD.md`。建议采用以下头部：

```yaml
---
title: {合同名称}起草前提要
date: YYYY-MM-DD
client_side: 甲方/乙方/待确认
status: 待律师确认
law_verification: 已核验/部分核验/待核验
---
```

将文件链接发送给用户并暂停合同正文起草。用户确认或提出修改后，更新同一文件的结论和`status`，再进入正文起草。除非用户明确要求跳过该步骤，不得在未确认起草逻辑时直接完成合同。

合同标题和“项目性质/合作模式”应正面、完整地描述真实安排。不要依赖“本项目不构成……”等否定式标签规避监管；监管定性取决于实际行为、对价和资料用途。

需要具体检查表时，读取 [references/drafting-standard.md](references/drafting-standard.md)。

## 三、设置澄清门槛和确认门槛

材料足够时直接起草，不做形式化追问。仅当未知事项会改变下列任一内容时，先与用户确认：

- 法律关系或监管属性；
- 合同相对方、客户立场或市场地位；
- 对价性质、付款路径、税票处理；
- 交付物、验收标准或核心时间节点；
- 数据、肖像、知识产权、品牌或成果的用途边界；
- 解除、赔偿、担保或其他重大风险分配。

每轮优先提出 1—3 个问题。能够列出互斥方案时使用多选项并说明影响；不能穷尽时允许自由回答。不要询问可从文件查明或可用占位符解决的普通信息。

如重大问题未确认且不同答案会导致起草前提要或合同结构实质变化，应先完成必要澄清；如仅影响可填写数据，则在前提要中列明，并在合同中使用统一占位符。

完成必要澄清后先交付起草前提要。律师确认的是法律关系、法律依据、合同结构和主要风险分配，不要求先确认全部普通填写项。

## 四、按客户视角设计合同

先确定客户是何方、市场地位为强势/平等/弱势、哪些风险由其实际控制。正文遵循以下规则：

1. 将主要履行义务、资质保证、真实性保证、交付、通知和配合责任写给最能控制该事项的一方；
2. 优先强化相对方可履行、可验证、可追责的义务，并为客户保留验收、暂缓履行、补救、解除和索赔抓手；
3. 客户依法必须履行或交易不可缺少的义务，应准确写入正文，不得为了“有利”而删除；
4. 仅属客户内部操作、用途控制或发布前审查的合规提示，原则上写入批注，不主动扩张为对相对方的合同义务；
5. 低风险、容易履行且确有对等价值的条款可以双向约定；不要机械追求形式对等；
6. 不使用明显失衡、无法执行或可能作为格式条款失效的保护方式。

正文只写对外合同语言，不出现“提请公司注意”“建议客户”“我方风险”等内部视角。

## 五、建立履行闭环

根据法律关系智能增删条款，不机械套用固定目录。通常按以下逻辑组织：

1. 主体、鉴于、定义及项目性质；
2. 资质、陈述与保证；
3. 标的/服务范围及履行标准；
4. 交付、查验、补正、验收及隐蔽问题；
5. 对价、付款条件、发票及对公账户；
6. 与交易相关的数据、保密、知识产权、品牌、合规条款；
7. 风险事件的通知、处置、保存和配合；
8. 期限、变更、解除及终止后处理；
9. 一般违约、重大违约、迟延责任、损失范围和实现权利费用；
10. 不可抗力、通知送达、法律适用、争议解决、生效及附件。

每项核心义务尽量形成：

`义务主体 → 履行内容 → 标准/期限 → 证据 → 验收/确认 → 不合格补救 → 付款影响 → 解除/违约责任`

附件只承载需要反复填写或项目化选择的操作信息，如清单、价格表、里程碑、验收标准和项目确认单。不能把关键风险分配留在不存在或未提供的附件中。

## 六、法律研究与依据使用

项目 wiki 中已有经核验且稳定的口径，可作为起草起点。遇到新类型、高监管事项、现行性可能变化、需要正式引用条文号或用户要求核验时，先使用已配置的法律 MCP；无法使用时再以国家机关官方来源核验。

合同正文以明确权利义务为主，一般不堆砌法条。法律依据主要用于：

- 确定合同结构和强制性边界；
- 支撑内部批注；
- 解释为何必须修改业务安排；
- 在确有必要时写入鉴于或合规承诺。

不得照搬未经复核的模板法条、比例、期限或结论。

## 七、批注采用“依据—理由—建议”

仅对客户需要决策、留痕或执行提醒的事项设置批注。每条批注原则上只处理一个问题，并使用以下三段：

> 依据：列明现行法律、监管规则、客户文件或已确认事实；引用法条时核对名称、条号和现行性。  
> 理由：解释该依据如何作用于本交易、为何正文采用当前写法以及主要风险。  
> 建议：给出客户可执行的签约前确认、流程控制、材料留存或后续升级方案。

批注应锚定具体文字，避免大段法条摘录和泛泛提示。以下内容不能只留在批注：合同标的、核心对价、验收标准、法定必备条款、必须由相对方承担的责任及重大解除条件。

## 八、按 Agent 能力生成交付稿

skill 组合是首选方式：本 skill 负责事实、法律关系、合同结构和条款内容，Agent 自带的 documents/Word skill 或等效能力负责 DOCX、批注、样式和文件验证。自带 skill 通常效率更高、能力更完整，不应为了统一而绕过。

起草前先检查当前 Agent 能力，并按以下顺序处理：

1. **存在 Agent 自带的 documents/Word skill 或等效 DOCX skill**：直接调用，由其生成 DOCX、添加批注并按其规则验证。这是默认路径。
2. **不存在上述能力**：调用内置`scripts/build_contract_docx.py`，将已确认的合同正文纯文本转换为基础清洁 DOCX。脚本只使用 Python 标准库，无需把大型文档工程说明加载进上下文。

脚本调用方式：

```bash
python3 "<本skill目录>/scripts/build_contract_docx.py" "/绝对路径/合同正文.txt" "/绝对路径/{合同名称}_YYYYMMDD.docx"
```

纯文本首个非空行作为标题，其余每个非空行作为一个段落；可使用`[[PAGE_BREAK]]`、`[[SIGNATURE_PAGE]]`、`[[CENTER]]`和`[[NO_INDENT]]`控制少量必要格式。该纯文本仅是转换输入，不作为用户交付物。脚本输出基础清洁稿，不声称具备复杂表格、客户模板保真、批注或修订能力；这些需求应使用 Agent 自带文档 skill。脚本生成后必须检查 DOCX 包结构，并抽查标题、正文层级、签署页和页码。

生成Word时遵守项目的作者、时间、命名和格式规则；本机无更近端规则时，批注及修订作者使用“lawyer”，时间使用中国标准时间`+08:00`，多处批注或修订按实际审阅顺序递增。

- 有客户模板：保留版式、样式和既有编号，做最小必要格式调整；
- 从零起草：自带文档 skill 路径交付清洁正文加必要内部批注；轻量脚本路径交付清洁正文，内部说明保留在起草前提要；
- 基于既有草案重构：用户要求看差异时使用 Word 修订模式；
- 不在合同正文附加 AI 免责声明，除非用户明确要求；
- 生成后检查正文、批注、作者与时间、交叉引用、编号、占位符和附件；
- 按所调用文档工具的规则验证。没有强制渲染要求时，默认做结构检查和关键页面抽查；转换文件、复杂表格、签章区异常或用户明确要求时再升级为逐页检查。

文件名遵守适用的`AGENTS.md`；无规定时，清洁生成稿使用`{合同名称}_YYYYMMDD.docx`，不得添加“修订稿”等字样。只有基于既有合同输出红线且用户要求展示差异时，才按合同审查规则使用修订稿命名。

## 九、最终质量门槛

交付前逐项确认：

- 合同名称与真实交易一致，复合关系已拆清；
- 起草前提要已保存并经律师确认，合同未偏离确认后的法律关系和结构；
- 客户立场贯穿付款、验收、风险、解除、管辖和违约；
- 核心履行闭环可操作，未把重要事项留作空泛协商；
- 资金、货物、发票、数据、知识产权和品牌使用边界一致；
- 一般违约、重大违约、解除条件、终止后处理彼此衔接；
- 术语、金额、期限、交叉引用、编号和附件一致；
- 正文没有内部建议，批注没有替代应写入正文的义务；
- Word交付已完成与当前能力相匹配的结构检查；使用轻量脚本时已说明其不包含复杂模板保真、批注和修订能力。

最终向用户简要说明：已确认的起草前提要、合同交付文件、仍需填写或确认的事项、法律依据核验状态、采用的文档能力及实际完成的检查范围。
