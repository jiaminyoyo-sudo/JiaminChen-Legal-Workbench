# 通用中国律师函生成器

## 基本原则

以律师函签发专家的结构、排版和签发规则为默认基线，并保留已确认的工程边界：

- 模型负责法律关系、签发目的、优劣势、可能抗辩、证据边界、函件策略、法律分析和措辞；
- 法律 MCP 负责核验现行法、必要案例和主体信息；
- 代码负责事项字段、11 部分完整性、形式要件、草稿/签发状态、占位符、DOCX 生成、包部件保留和版式审计；
- 律师负责事实、证据状态、请求强度、客户确认、法律判断、两名经办律师、签发日期、附件、盖章和是否发送。

固定 11 部分是默认且必要的文书骨架，不得再用自由目录替代。不同法律关系可以改变每部分的内容、长短和表达重点，但不得静默删除案号、摘要、法律责任、本律师意见、签署或附件。

需要完整理解固定结构、七道签发控制、排版和送达规则时，读取 references/structure-and-issuance.md。生成事项 JSON 前读取 references/matter-schema.md；处理证据缺口时读取 references/drafting-and-evidence.md；使用信头时读取 references/template-contract.md。

## 工作流

### 一、读取事项上下文

1. 读取当前目录及上级 AGENTS.md；存在客户 Wiki 时按项目规则读取索引和相关页面。
2. 读取合同、函件、邮件、聊天、付款记录、通知、截图和其他材料。
3. 确认七项输入：签发目的、委托人、收件人及送达地址、事由或法律关系、核心事实、委托人诉求、不履行后果；附件按实际情况补充。
4. 不机械地逐项追问。缺口会实质改变法律关系、请求或风险时集中提问；律师要求先出稿时，以限定表述或占位继续形成审阅稿。

### 二、先判断法律关系和签发策略

至少判断：

- 谁基于何种合同、侵权、身份、法定或监管关系向谁主张什么；
- 律师函是履行催告、解除通知、停止侵害、澄清立场、获取信息、保全权利、谈判还是其他法律效果；
- 委托人的优势、劣势、风险，以及律师函能否实现目的；
- 是否存在期限、解除权、通知到达、诉讼时效、管辖、主体资格、损失证明、行政或刑事风险；
- 对方最可能提出的事实和法律抗辩；
- 函件应采用强硬、克制、谈判、通知或权利保留口径。

把结论记录在 strategy_analysis，不要把内部优劣势分析机械照搬进正文。只有结构性判断成立后再写 11 部分正文。

### 三、按需核验法律和主体

1. 优先使用直接可调用的法宝；法宝未暴露、调用失败或不可用时立即使用元典。
2. 法条使用 yuandian-law，案例边界使用 yuandian-case，企业名称、登记和主体状态使用 yuandian-company。
3. 只写已核验且与具体主张直接相关的依据，不为显得专业而堆砌法条。
4. 区分法律明确规定、裁判通常处理、合同约定和律师策略判断。
5. 对利息、损失、违约金、律师费、行政责任、刑事责任、失信后果等条件性结论保留触发条件。

不得使用模型记忆冒充现行法核验结果。

### 四、处理事实和证据

证据不足不是拒绝起草或当然拒绝签发的理由，也不生成单独审查单。

对每项重要事实记录：

- 事实陈述；
- 现有证据；
- 尚未提供但通常需要的最基础证据；
- 是否写入律师函；
- 律师选择：有证据确认、无证据仍确认、限定表述或删除。

运行：

~~~bash
python scripts/validate_matter.py matter.json
~~~

草稿只有警告时继续起草。不得虚构证据名称、形成时间、金额、送达、签收、催告次数或客户确认。没有证据时，根据律师选择使用“据委托人陈述”“根据现有材料”“现有信息显示”“请贵方核实”等表述。

“主要依据/事实依据”只列实际已经取得并准备作为函件基础的材料；基础应有证据在交付消息中提示；附件只列实际决定随函发送的材料，三者不得混同。

### 五、按固定 11 部分起草

严格依次形成：

1. 标题；
2. 案号；
3. 摘要；
4. 首部；
5. 一、主要依据，下分事实依据和法律依据；
6. 二、基本事实；
7. 三、法律责任；
8. 四、本律师意见；
9. 结尾；
10. 签署；
11. 附件。

纯通知类函件仍应在“法律责任”说明通知的法律效果、对方配合义务或不履行后果。没有附件的签发稿写“附件：无”。不得用“有关事实、委托人立场、正式要求、权利保留”等自由目录替换固定四个一级标题。

草稿标题仍使用“律 师 函”，不在正式标题中加入“律师审阅稿”。草稿身份由待编号、手签栏、附件提示和交付消息识别。

### 六、执行签发控制

审阅稿可以在委托、证据、客户确认、编号、律师和附件尚待补充时生成。转为 final 前确认：

1. 签发目的明确；
2. 委托手续完备；
3. 11 部分完整；
4. 已完成优劣势、风险、目的适配和证据状态分析；
5. 签发策略经客户确认；
6. 函稿经客户书面确认；
7. 请求、期限、后果、排版、两名律师、日期、盖章、骑缝章和附件均据实核对。

证据没有全部取得不当然阻止 final；但每项拟写入的重要事实必须有律师选择。final 必须设置 lawyer_confirmed: true，并通过验证器，不得仍有占位符。

### 七、生成和审计大成信头 DOCX

使用 assets/大成成都信头纸模板.docx，始终复制后写入，不修改资产原件。

~~~bash
python scripts/build_letter_docx.py \
  --input matter.json \
  --template assets/大成成都信头纸模板.docx \
  --output /absolute/path/事项_律师函_DC_修订稿YYYYMMDD.docx

python scripts/audit_letter_docx.py \
  /absolute/path/事项_律师函_DC_修订稿YYYYMMDD.docx \
  --template assets/大成成都信头纸模板.docx
~~~

生成器执行：

- 草稿案号为空时生成“编号：（当年）川大成函字第〔待编号〕号”；
- 律师不足两名时保留两处“经办律师：＿＿＿＿＿＿＿＿（手签）”；
- 日期为空时按生成当日中国标准时间预填中文日期，提醒律师据实修改；
- 始终保留“（本函加盖本所公章及骑缝章后发出）”；
- 按 11 部分输出正文并保留信头、首页/续页页眉页脚和页码字段；
- Word 作者和最后修改者写入“大成律师”，时间使用中国标准时间。

### 八、渲染和逐页检查

1. 优先用当前 Agent 的 Documents 能力运行 render_docx.py；
2. 如隔离 HOME 导致中文字体显示方框，使用 scripts/render_letter.py 保留本机字体环境；
3. 逐页检查信头、标题、编号、摘要、四个一级标题、正文、分页、签署块、两处手签、中文日期、盖章提示、附件和页码；
4. 如有缺字、裁切、跨页拆散、异常留白或包部件变化，修改后重新生成、审计和渲染；
5. 签发稿默认同步生成 PDF，并核对 PDF 与 DOCX 内容和分页；审阅稿仅在用户要求时生成 PDF。

## 交付

默认交付经审计和渲染核验的 DOCX；签发稿同时交付 PDF。文件名使用 _DC_修订稿YYYYMMDD 后缀。

交付消息简要列出：

- 已有材料；
- 尚缺基础证据；
- 请律师据实检查的主体、地址、金额、日期、期限、送达、定性、请求、编号、两名律师、盖章、骑缝章和附件；
- 需要律师选择的无证据仍写入、限定表述、删除或继续补证。

不另行生成审查单，不自动签名、盖章、寄送或向第三方发送。

## 质量检查

- 法律关系、签发目的、诉求和不履行后果是否一致；
- 优劣势、风险、对方抗辩和函件适配性是否已经分析；
- 11 部分是否完整，四个一级标题是否固定；
- 事实依据是否只列实际取得的材料；
- 事实、证据状态和律师选择是否对应；
- 法条、案例、主体、金额和期限是否核验；
- 是否误把可能后果写成必然后果；
- 编号、两名经办律师、中文日期、公章及骑缝章提示、附件是否完整；
- 页边距、字体、行距、信头、续页、页码和分页是否合规；
- DOCX 包是否只改变允许的部件；
- 签发稿是否仍有占位符或版式缺陷。

## 边界

本 Skill 生成供律师复核和签发的律师函，不替代律师执业判断，不自动签名、盖章、寄送或向第三方发送，也不得未经授权把客户材料保存到项目范围外。
