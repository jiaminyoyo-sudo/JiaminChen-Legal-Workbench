# 中国法律调研备忘录

## 目标

把法律检索、事实适用和正式成文连成一条可复核的工作链。交付物应当回答客户提出的问题，说明答案成立的条件和边界，并让律师能够从每项重要主张追溯到项目材料、现行规范、案例或监管来源。

## 适用边界

使用本技能处理需要书面研究成果的中国法事项，包括：

- 单一专题的法律备忘录；
- 多问题、跨规范层级的综合调研；
- 案例、监管处罚、交易所问询或地区政策的比较研究；
- 新业务模式、重大交易或合规方案的可行性论证；
- 将既有短答复扩展为可供客户或决策机构使用的 Word/PDF 文件。

下列任务另行路由：

- 只需逐问给出短答复，且不要求形成正式研究文件：使用 `china-regulatory-consulting`；
- 审查、修订已有合同：使用 `contract4`；
- 从业务方案起草合同：使用 `china-contract-generator`；
- 需要系统类案检索和全文归档：并用 `case-research`；
- 需要制作或编辑 DOCX/PDF：并用当前可用的 `documents`、`pdf` skill。

## 必须读取的参考文件

开始研究前读取：

- `references/research-method.md`：研究步骤和分析单元；
- `references/source-verification.md`：来源层级、现行性和案例核验；
- `references/team-style.md`：团队语体和版式特征；
- `references/output-structures.md`：按任务选择成文结构；
- `references/model-code-boundary.md`：模型、脚本、来源与律师的责任边界。

需要说明本技能的外部方法来源或许可边界时，再读取 `references/design-provenance.md`。

## 工作流

### 一、读取项目并建立事实底稿

1. 读取项目级 `AGENTS.md`、工作规则、索引和本次相关材料。不得跳过更近层级的项目规则。
2. 建立“已确认事实—材料中主张—尚待核实—本次假设”四栏底稿。材料中的陈述不自动等于已确认事实。
3. 记录适用法域、基准日期、委托目的、预期读者、交付格式及保密边界。
4. 只补问会改变研究路径的关键事实。可以从材料中确定的，不重复询问；暂不影响检索方向的缺口，标注假设后继续。

### 二、把客户问题改写成问题树

保持客户原问题的顺序，同时拆成可分别回答的法律命题。每个命题至少写明：

- 审查对象和法律关系；
- 控制性问题；
- 适用条件或法律要件；
- 可能支持结论的材料；
- 可能限制或推翻结论的反向问题；
- 结论将影响的业务选择。

不要先写百科式背景。问题树应当服务于最终答案。

### 三、先做检索计划，再检索

按问题建立“主张—来源台账”。可以使用 `scripts/source_ledger_audit.py` 所列字段。对每个决定性问题至少安排：

1. 控制性现行规范；
2. 定义、适用范围、例外、程序和责任条款；
3. 实施规则、主管机关文件或监管实践；
4. 支持本方结论的案例或实例；
5. 限制本方结论的案例、处罚或相邻案型；
6. 无直接依据时的替代检索路径和检索局限记录。

先做小样本检索，确认关键词、案型和接口是否匹配，再扩展。不得用检索结果数量代替相关性判断。

### 四、核验来源

法律、法规、司法解释、部门规章、地方规则和案例，优先通过项目规则指定的法宝或元典 MCP 核验；法宝不可直接调用或调用失败时，立即转元典。必要时用国家机关、法院、检察院、监管机关、交易所等官方原文复核。

每项重要法律主张至少记录：名称、制定或发布机关、效力层级、文号或案号、条款或页码、公布与施行日期、当前效力、核验日期、法宝或元典链接；存在公开官方链接时一并保留。法规正文、案例裁判理由和二手解读不得混为同一层级。

不得从记忆补写具体条文、案号、日期、金额、比例或监管口径。检索不到时，缩窄结论并说明未核验部分。

### 五、按分析单元完成论证

每个决定性问题按下列顺序展开：

1. **本节结论**：先用一至三句话回答问题，并写明成立条件；
2. **规范基准**：说明控制性规则、规范层级及适用要件；
3. **事实适用**：逐项比对现有事实，不把事实缺口补成既成事实；
4. **支持材料**：说明案例、监管实例或实践材料为何可比；
5. **限制因素**：处理反向规则、相邻案型、程序障碍和不同口径；
6. **初步判断**：区分法律上可否、程序上能否办理、监管上是否接受、证据上能否证明；
7. **建议路径**：给出可执行方案、前置条件、留痕要求和需要进一步确认的事项。

法条仅完成了“规范基准”。必须继续写事实适用和限制因素，才能形成法律分析。

### 六、选择成文结构

根据 `references/output-structures.md` 选择一种主结构：

- 聚焦型专题调研；
- 多地区、多规则或多案例比较调研；
- 正式客户法律备忘录。

标题层级可以随问题复杂度调整，但背景、问题、分析、结论或建议、来源核验信息不得缺失。结论部分按客户原问题顺序回收答案，不另起一套编号。

### 七、按团队风格成稿

遵循 `references/team-style.md`。主要要求是：

- 先结论后理由，长句用于完整论证，短句用于收束判断；
- 用“经核查”“我们理解”“初步判断”“谨提示”等表达证据状态和判断边界，不密集堆叠；
- 区分已确认事实、材料陈述、法律规定、监管实践、案例观点和本团队推断；
- 直接说明没有完全相同案例、主管部门实操仍需确认等研究局限；
- 建议不仅指出最严格底线，还要说明可落地路径及其条件；
- 表格只用于固定字段比较，不把核心推理藏在表格中。

### 八、交付前进行两轮复核

第一轮是法律复核：

- 对每项决定性主张回到原始来源；
- 核对法规现行性、条文定位、上下位法和配套规定；
- 核对案例全文、裁判层级、审级、裁判日期及后续状态；
- 主动查找反向依据，检验结论是否过宽；
- 检查法律许可、行政办理、监管接受和商业选择是否被混写。

第二轮是机械复核：

```bash
python3 scripts/research_memo_audit.py <备忘录.md或.docx> --output <检查报告.json>
python3 scripts/source_ledger_audit.py <主张来源台账.csv> --output <台账检查报告.json>
```

脚本通过不代表法律结论正确。脚本只能发现结构、占位符、引证字段、重复编号、链接和台账缺项；实质结论仍须由模型完成论证并由律师审定。

### 九、生成并检查正式文件

如用户要求 DOCX/PDF：

1. 保留原始材料，成果文件按项目命名规则保存；
2. 通过 `documents` skill 生成或编辑 DOCX，作者和修订者使用项目指定名称；
3. 保留可点击的法宝或元典链接；能够同时提供官方公开链接的，一并保留；
4. 通过渲染逐页检查标题、分页、表格、脚注、页码、链接和孤行；
5. PDF 由已核验的 DOCX 导出，再抽取文字和渲染页面复核；
6. 交付前再次运行两个审计脚本，并记录尚待律师确认的实质事项。

## 不得跨越的边界

- 不把二手文章写成法律依据；二手资料只能帮助定位原文或说明实务争议。
- 不因未检索到反例就断言不存在反例。
- 不以单一基层案例概括全国统一裁判规则。
- 不把地方主管部门口头答复表述为普遍适用的法律结论。
- 不把“法律未明文禁止”直接写成“可以实施”。
- 不擅自确定客户未确认的事实、商业目标、风险偏好或对外口径。
- 不把脚本检查结果写成“法律审核通过”。

## 完成标准

只有同时满足下列条件，方可标记为可交律师复核：

- 客户问题均有明确答复，且顺序可对应；
- 每项决定性法律主张能够回溯至已核验来源；
- 结论写明适用条件、限制和事实缺口；
- 至少完成一次反向检索或说明无法完成的原因；
- 建议路径写明前置条件、实施步骤和留痕事项；
- 结构审计和来源台账审计无阻断项；
- DOCX/PDF 已完成结构检查和逐页渲染检查；
- 律师尚需作出的判断被单独列明，没有被模型或脚本代替。
