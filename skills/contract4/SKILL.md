# Contract Review and Minimal Redlining

## 目标

形成律师可快速复核、客户可直接阅读的 `.docx` 修订稿。评价标准不是“条款写得更完整”，而是：

1. 重要风险被准确处理；
2. 原合同结构、表达和商业安排被最大限度保留；
3. 修订痕迹足够小，能够一眼看出改了什么；
4. 新增义务与交易复杂度、实际执行能力相匹配；
5. 正文、违约责任和附件前后勾稽；
6. 核心修改有面向客户的简洁批注。

## 一、规则优先级

依次遵循：

1. 用户在本次任务中的最新明确意见和已经确认的取舍；
2. 项目级 `AGENTS.md`、客户 wiki 及事项材料；
3. 合同正文、附件和真实交易事实；
4. 本 Skill 的通用规则。

不得为了套用本 Skill 而推翻用户已经确认“不改”或“只批注”的事项。

## 二、强制原则

### 1. 默认不修改

发现表述不够漂亮、不够严谨或存在更常见写法，不等于需要修订。只有问题会实质影响交易目标、责任边界、履行、验收、付款、救济、监管、证据或争议结果时，才进入修改候选。

原文已经能够表达同一法律效果，或者后果能够从既有先后履行关系和法律规则直接得出时，不重复增加同义条款。

### 2. 双重最小化

- **法律内容最小化**：能删改一个字词，不改整句；能补一个短句，不替换整段；只有原段逻辑无法局部修复时才重写。
- **Word 痕迹最小化**：只对真正变化的字符写入 `w:ins`、`w:del`，不得把未变化的文字一并标红。

“原文＋补充”能够解决问题时，不把原文全部删除后换成律师式完整版本。

### 3. 重要性高于完整性

不为覆盖审查清单而强行补齐所有机制。不修改不会改变实质结果的惯用表达，不把法定或上下文当然结果重复写入合同，不为“更专业”增加不必要的程序。

### 4. 可执行性和比例性

根据交易金额、业务复杂度、履行频率和客户管理能力设置通知、申请、审批、书面记录和证据要求。简单服务或小型安装工程，不默认要求盖章变更单、多层授权、逐项测试、全程影像等重程序。

### 5. 商业分配未知时只批注

设备进场、物业协调、高空作业手续、费用承担、审批主体等存在多种合理分配，且合同与附件不能确认时：

- 不直接把义务和费用改给任何一方；
- 在对应条款作客户口径批注，列明需要确认的选项及影响；
- 客户确认后再作最小正文修改。

### 6. 全文和附件必须勾稽

新增“以附件约定为准”“附件明确列明的除外”等表述前，必须实际检查附件是否存在对应项目。没有对应内容时，选择：

- 不增加该引用；或
- 同时对附件作最小修改并加批注。

不得生成不存在的附件、标准、承担项目或书面确认机制。

### 7. 履行义务与违约责任分层

- 业务条款写“谁在何时做什么、达到什么标准”；
- 程序条款写通知、验收、整改和确认；
- 违约责任章写不履行后的违约金、赔偿、解除及费用承担。

仅在立即整改、暂停使用等救济必须与流程相连时，才在业务条款中写即时后果。避免把程序、责任和证明要求揉成一个长段。

### 8. 正式元数据和原件保护

- 默认生成副本，不覆盖原件；
- 文件名使用 `_DC_修订稿YYYYMMDD`；
- 修订者、批注作者使用 `lawyer`；
- 时间使用中国标准时间 `+08:00` 并按审阅顺序递增；
- 保留其他作者既有修订和批注，不擅自接受或拒绝。

## 三、准备和定位

从对话、项目规则、客户 wiki、背景材料、正文和附件确认：

1. 我方代表哪一方及市场地位；
2. 真实交易、标的、对价、业务流程及实际参与方；
3. 哪些设备、材料、成果由谁提供，哪些属于甲供、利旧或第三方提供；
4. 特别关注事项及用户已确认的“不改／只批注／直接修改”；
5. 文件是否已有修订、批注或复杂结构。

仅在缺失信息会实质改变修订方向时提问。信息足以继续时，明示作业假设，不因追求完整而暂停。

开始 Word 修订前，向用户给出 5—10 行修订前提要；用户已经逐条给出意见时，概括执行口径后直接修订。

复杂交易、新业务、高监管或法律关系不清时，完整读取 [合同审查法律框架](references/contract-review-framework.md)。

## 四、修改闸门

制定操作清单前，对每个候选修改在内部依次判断：

1. 原文具体造成什么风险，而不是“还能写得更好”；
2. 原文或上下文是否已经覆盖；
3. 法律是否已经直接产生相同后果；
4. 该风险是否重要到需要改变正文；
5. 是否属于未确认的商业选择，应改为批注；
6. 最小修改单位是字、词、短语、短句还是整段；
7. 修改是否增加客户或对方难以执行的程序义务；
8. 是否影响违约责任、定义、附件或其他交叉引用。

结论只能是以下四类之一：

| 结论 | 适用情形 |
|---|---|
| 不修改 | 仅属表达习惯、已有覆盖、当然后果或风险轻微 |
| 仅批注 | 商业选择未确认、事实不足、风险提醒或履行建议 |
| 局部红线 | 可通过字词、短语或单句解决的重要问题 |
| 结构性修订 | 局部操作无法形成核心交易或责任闭环；必须说明理由 |

在生成操作清单前，必须完整读取 [最小修订与批注规则](references/minimal-revision-playbook.md)。

## 五、核心闭环

优先审查：

1. 标的和范围；
2. 交付、工期和变更；
3. 质量标准、验收、整改和质保；
4. 价款、付款、发票和结算；
5. 资质、分包、第三方权利和监管要求；
6. 关键违约、解除、退款、赔偿和损失范围；
7. 附件与正文的对应关系。

### 违约责任

先将修改后的正文义务与违约责任逐项对照：

- 核心义务采用有触发条件、有补救路径的专项责任；
- 非核心义务由通用违约责任兜底；
- 违约金不足以覆盖损失时，再约定补足；
- 损失范围是否列举，应结合客户是主要权利方还是主要责任方决定；
- 不为每项程序义务分别堆叠违约金。

### 质量问题

涉及设备、材料或施工时，区分：

- 一般质量不合格或产品瑕疵；
- 施工、安装质量；
- 危及人身、财产安全的产品缺陷；
- 甲供、利旧和乙方提供的新增设备材料。

标准、验收、整改、质保和违约责任必须能够相互引用，但不得把全部内容塞进同一条。需要法律核验时，先使用项目指定的法规、案例来源。

## 六、批注

### 必须优先批注

- 会实质改变费用或责任承担、但事实未确认的商业条款；
- 核心红线修改的依据和上下文勾稽；
- 需要客户选择的期限、比例、手续主体或执行方案；
- 条款表面对客户有利但存在法定边界；
- 附件缺项、定义冲突或其他条款需同步调整。

### 批注口径

批注直接面向接受法律服务的公司经办人员，不写内部审查指令。涉及核实事实、确认方案或提示后续动作时，统一使用“请公司确认／核实／结合实际处理”等表述；不得写“请客户确认”“建议客户”等律师内部工作称谓。存在多个关联主体时，写明具体公司或合同主体，避免“公司”指代不清。

对法定边界、条款效力或责任可能被调整的核心修改，采用“法律边界＋核心理由＋公司动作”三层批注：

1. 用简明语言说明适用规则及其法律后果，不堆砌法条原文；
2. 说明本处为何修改、删除或暂予保留，以及对公司利益和条款稳定性的实际影响；
3. 对仍取决于事实或商业选择的部分，明确请公司填写、确认、决定或留存的材料。

必须区分法律、司法解释形成的裁判边界与行政合规指引、行业惯例等参考标准，不得把“通常”“一般不宜”等参考口径写成强制法定标准。

通常采用：

```text
本处建议……。主要考虑是……；如实际由……承担，请公司确认后据此调整。
```

批注应说明实质理由，可基于市场惯例、法律规则、执行难度或上下文逻辑。不要只写“旅行体制”“商务提示”“请确认是否接受”等空泛标签，也不要给每个标点或纯技术修改加批注。

## 七、Word 操作

1. 先形成 JSON 操作清单；
2. 优先使用 `replace`、`delete`、`insert_before`、`insert_after`；
3. 运行脚本的操作范围检查；
4. 再写入 Word 修订；
5. 结构性修订必须在操作中填写 `allow_broad_change: true` 和具体 `reason`；
6. 核心修改同步添加客户口径批注。

小粒度修订使用：

```text
scripts/precise_revision.py
```

操作、已有修订、复杂 Run、批注和验证规则，完整读取 [Word 红线工程规则](references/docx-redline-engineering.md)。

## 八、验证

除 DOCX 结构检查外，至少完成：

1. 抽查接受修订后的关键文本；
2. 检查是否存在可拆成局部修改的整句、整段替换；
3. 核对每项新增商业义务是否已有事实依据或客户确认；
4. 核对正文、定义、违约责任和附件的交叉引用；
5. 核对利旧、甲供、乙方新增范围是否混淆；
6. 核对核心修改是否有客户口径批注；
7. 检查批注对象称谓：应使用“公司”或具体合同主体，不得出现“请客户”“建议客户”等内部称谓；
8. 检查法律边界型批注是否同时说明规则后果、修改或保留理由及公司后续动作，并区分强制规则与参考标准；
9. 确认未因“更完整”增加无法执行的程序。

发现大段修订时，先回退并重新拆分；不能拆分的，保留结构性修改理由。

## 九、交付

默认交付：

- 一份带原生修订和必要批注的 Word 副本；
- 简短说明文件路径、修订数量、核心修改和待客户确认事项。

除非用户明确要求，不另行生成长篇审查报告、谈判策略或重复性 Markdown 文档。
