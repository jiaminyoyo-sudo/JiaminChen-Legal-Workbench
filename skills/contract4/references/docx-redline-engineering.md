## 1. 安全边界

- 默认保留原文件并输出`_DC_修订稿YYYYMMDD.docx`副本。
- 仅在用户明确要求时使用`--in-place`。
- 修订前确认文件能作为ZIP解压，至少存在`[Content_Types].xml`和`word/document.xml`。
- 不擅自接受、拒绝或合并其他作者修订。
- 文档损坏、正文缺失或关系文件异常时停止，不在损坏包上猜测修复。

## 2. 工具选择

### 首选精准脚本

局部替换、删除和短句插入使用：

```text
scripts/precise_revision.py
```

先运行 `--check-only`，确认操作范围和锚点，再正式写入。不得以整段文本作为替换内容，只因为这样更容易定位。

### 使用稳定文档工具

涉及大量批注、复杂表格、文本框、脚注、域、书签、超链接或整体结构时，使用稳定的文档处理工具，并遵循其渲染验证要求。

### 早期helper

`revision_helper.py`和`comment_helper.py`保留用于兼容旧任务，不作为新任务首选。它们对复杂Run、关系文件、时区和并发安全的覆盖弱于当前流程。

## 3. 精准修订脚本

### 操作文件

```json
[
  {
    "type": "replace",
    "target": "15日",
    "replacement": "30日",
    "paragraph_hint": "收到资料后15日内完成确认"
  },
  {
    "type": "delete",
    "target": "唯一",
    "paragraph_hint": "唯一著作权人"
  },
  {
    "type": "insert_before",
    "anchor": "。",
    "text": "，但双方另有书面约定的除外",
    "paragraph_hint": "本条款自合同生效之日起适用"
  }
]
```

当同一目标出现多次时使用`occurrence`，并尽量提供具有唯一性的`paragraph_hint`。

### 预检

```bash
python3 scripts/precise_revision.py '合同.docx' '/tmp/ops.json' \
  --author 'lawyer' \
  --start-time '2026-07-20T09:30:00+08:00' \
  --check-only
```

只有预检通过后再正式写入。

### 正式调用

默认生成新副本：

```bash
python3 scripts/precise_revision.py '合同.docx' '/tmp/ops.json' \
  --author 'lawyer' \
  --start-time '2026-07-20T09:30:00+08:00' \
  --print-summary
```

明确需要原地修改时：

```bash
python3 scripts/precise_revision.py '合同.docx' '/tmp/ops.json' \
  --author 'lawyer' --in-place --print-summary
```

脚本支持`replace`、`delete`、`insert_before`、`insert_after`。`replace`会提取公共前后缀，只对真正变化部分写入修订。

## 4. 操作范围闸门

脚本按“可见修订范围”检查操作，而不是按定位锚点长度检查：

- `replace`只计算公共前后缀之外真正删除、新增的部分；
- `delete`计算被删除文本；
- `insert_before`、`insert_after`计算新增文本；
- 默认可见变化超过80字或跨越一个以上句界时拒绝执行。

确实无法局部修复核心法律关系时，逐项声明：

```json
{
  "type": "replace",
  "target": "原条款全文",
  "replacement": "新条款全文",
  "paragraph_hint": "原条款开头",
  "allow_broad_change": true,
  "reason": "原条款混合两个责任主体且局部增删仍会产生矛盾"
}
```

`reason`必须说明为什么不能通过字词、短语或短句修复。不得使用“表述更规范”“内容更完整”等理由。

结构性修订应同步添加客户口径批注，并在交付说明中单列。

## 5. 已有修订和复杂结构

- 新修订ID从文档现有`w:ins`、`w:del`最大数字ID后递增。
- 保留其他作者的修订包装，不把既有修订展开为普通文本。
- 精准脚本主要处理普通段落中的直接Run，以及正文、页眉和页脚。
- 目标位于超链接、文本框、内容控件、脚注、尾注、批注、域或既有修订内部时，不要强行运行局部脚本；改用能够处理相应结构的工具或精确OOXML方案。
- 涉及跨多个复杂Run的长段重写时，先判断能否拆成数个局部操作。

## 6. 批注

- 批注作者使用`lawyer`，时间使用`+08:00`并随审阅顺序递增。
- 批注范围尽量锚定具体词句，不默认覆盖整段。
- 新增`comments.xml`时必须同步维护文档关系和Content Types；已有批注时不得重用ID。
- 核心修订的批注优先采用：实质理由、上下文勾稽、客户操作建议。
- 商业责任分配未确认时，只添加批注，不把选项直接写成正文义务。
- 批注必须面向客户，不使用“内部审查”“风险点标签”等内部口径。
- 正式稿需要批注时，不因某个渲染工具兼容性而删除批注；可以另做无批注副本用于内部渲染。

## 7. 轻量验证

默认执行：

1. 使用`zipfile`或`unzip -t`检查DOCX包；
2. 解析所有已修改XML，确认无语法错误；
3. 统计新增`w:ins`、`w:del`及批注，核对作者、时间和ID；
4. 提取“接受修订后”关键文本，抽查与操作清单一致；
5. 对比修改前后的关键部件清单，确认没有意外缺失；
6. 确认原文件和输出副本均存在。
7. 审计操作清单，确认未隐藏绕过范围闸门的整段修订；
8. 抽查附件引用、定义和违约责任是否与正文同步；
9. 核对结构性修订是否有理由和客户口径批注。

不要求每次逐页渲染，也不要求页数绝对不变。

## 8. 升级检查条件

出现以下任一情况时增加渲染或人工重点检查：

- 文件由`.doc`或PDF转换；
- 原文已有异常分页、乱码或复杂历史修订；
- 大量修改表格、文本框、页眉页脚或签署页；
- 修改跨越多个段落或涉及编号、目录、域；
- 轻量检查发现结构、页数或关键部件异常；
- 用户明确要求正式版式验收。

检查目标是发现异常，不是追求修订前后像素级一致。
