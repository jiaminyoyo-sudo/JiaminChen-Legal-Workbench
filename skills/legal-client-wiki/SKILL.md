# 常年客户 Wiki

本 Skill 用于客户 Wiki 的冷启动、升级、跨事项专项编译和结构审计。它编译的是经律师确认的客户特有认知，不是外部法规、案例、文章或书籍的材料镜像库，也不是正式法律意见的替代品。

## 先判断工作模式

| 当前情况 | 处理方式 |
|---|---|
| 没有 Wiki，或只有零散旧页面 | 读取 [references/cold-start.md](references/cold-start.md) |
| 已有 Wiki，律师明确进入收尾 | 读取 [references/incremental-closeout.md](references/incremental-closeout.md) |
| 规则、目录、来源或当前/历史口径需要重构 | 读取 [references/rules-and-history.md](references/rules-and-history.md) |
| 需要跨事项批量补录或审计 | 读取 [references/audit-checklist.md](references/audit-checklist.md)，并运行 `scripts/audit_wiki.py` |
| 项目已经有完整 `wiki/规则.md`，只是单个事项日常增量 | 不加载本 Skill，直接按项目规则执行 |

先读取当前项目及上级 `AGENTS.md`。项目级入口只负责把 Agent 路由到 `wiki/规则.md`；客户 Wiki 的具体运行规则以该文件为唯一真实来源，不在 Skill 或 `AGENTS.md` 中静默覆盖项目约定。

## 不可违反的边界

- 不移动、覆盖或删除客户原始材料、历史定稿和证据文件。
- Agent 初稿、中间稿、未核验结论和无来源的取舍猜测不得直接进入长期 Wiki。
- 不把“律师采用了某句话”自动推导成客户通用规则，也不把“律师删除了某句话”自动推导成永久禁止。
- 当前事实、长期法律边界、商务选择、一次性谈判妥协和历史形成过程必须分开表达。
- 新材料与旧页面看似冲突时，先区分事实、主体、用途、时间、现行法、新证据和律师明确改口，禁止静默覆盖。
- 一次性低复用事项可以只登记来源和交付路径，不为页面数量制造知识。
- `scripts/audit_wiki.py` 只做确定性的只读结构检查，不判断法律结论，不批量修正页面。
- 项目级监控、定时轮询和自动回写不是本 Skill 的必要组件；是否使用由项目规则另行决定。

## 编译的核心判断

只把会改变后续办案、属于客户特有事实或流程、涉及创新/复合法律关系、形成稳定执行边界、需要高成本重新推导，或已在多个事项中重复验证的内容深编。编译前尽量结合修订符、批注、客户反馈、会议/通话记录和对话，还原：

```text
问题 → Agent 建议 → 律师接受/收窄/拒绝 → 取舍原因和条件 → 最终落地 → 可复用边界
```

所有长期页面都应能回到来源，并写清适用范围、例外、确认时间和当前/历史状态。

## 写入前的报告闸门

除用户明确要求直接写入外，冷启动、批量编译和规则升级先报告：

1. 候选新增、修改、历史保留和不编译内容；
2. 每项来源、确认状态、适用范围和拟写入位置；
3. 与现有页面的冲突、重复或证据缺口；
4. 将同步更新的 `索引.md`、`日志.md` 和 `原材料地图.md`。

等待律师确认范围后，再写入长期页面。成熟项目的单事项日常收尾也遵守项目 `wiki/规则.md` 设定的人工触发闸门。

## 交付后的检查

写入后检查：入口和索引可达；来源可回查；当前结论与历史过程没有混写；没有把个案妥协扩展成通用口径；原始文件未被修改；核心页面、日志和材料地图同步。结构问题可运行：

```bash
python3 scripts/audit_wiki.py check <项目>/wiki
python3 scripts/audit_wiki.py report <项目>/wiki --format markdown
```

遇到脚本报告的结构问题，先修正或向律师报告；不要让脚本代替内容判断。
