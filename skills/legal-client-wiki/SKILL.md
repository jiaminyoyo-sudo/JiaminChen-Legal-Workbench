# 常年客户认知编译

## 目标

把律师已确认的办案成果编译为可在后续事项中直接复用、可溯源且不会静默自相矛盾的客户认知。

核心产品不是文件数量，而是以下四类长期认知：

1. 公司发展历程和关键状态变化；
2. 主体、产品、业务模式及实际运行方式；
3. 创新业务、非标合作和其中的法律关系；
4. 已经律师确认的法律边界、适用条件、例外和执行要求。

事项页、合同页和时间线是上述认知的证据层，不是默认全量建设目标。

## 一、三层分工

### Skill：初始化和升级方法

本 Skill 用于：

- 为新客户搭建精简 Wiki；
- 从历史定稿和对话记录中冷启动编译；
- 改造旧客户 Wiki 的知识晋升及冲突规则；
- 跨事项专项编译、批量补录、知识体系重构或定期审计。

如项目已经存在完整的`wiki/规则.md`、`wiki/索引.md`、`wiki/日志.md`和`wiki/原材料地图.md`，且本次只是单个事项定稿后的日常增量编译，不再使用本 Skill 作为运行手册，直接按项目`wiki/规则.md`执行。只有项目规则缺失、需要升级、出现结构性冲突，或者用户明确要求专项审计、批量补录时，才重新进入本 Skill。

### 项目级 `AGENTS.md`：只做运行入口

项目级 `AGENTS.md` 只应说明：

- 本项目同步编译客户 Wiki；
- 处理客户事项时先读 `wiki/规则.md`；
- 再按该规则读取索引和相关页面。

不得在 `AGENTS.md` 重复 Wiki 页面结构、编译门槛、状态字段、索引日志规则或完整法律口径。

### `wiki/规则.md`：唯一的项目运行规则

客户的编译门槛、页面分类、定稿学习、冲突处理、状态和索引更新方式，全部以 `wiki/规则.md` 为唯一真实来源。

## 二、只从已确认定稿编译

### 可编译来源

优先级如下：

1. 律师已确认并对外发出的定稿；
2. 客户后续反馈并由律师确认的修订稿；
3. 签署稿、实际执行材料或客户明确确认的落地事实；
4. 支撑上述定稿的项目文件、现行规则和已核验来源；
5. 律师与 Agent 在形成定稿过程中的完整对话记录。

### 不进入长期 Wiki

- Agent 尚未经律师复核的初稿；
- 尚在来回修改中的中间版；
- 尚未核验依据的草案结论；
- 对未采用建议原因的无来源推测；
- 只因排版、文风或单次表达造成的差异。

未确认材料可进入原材料地图或待编译队列，不得写成客户长期知识。

## 三、对话驱动的定稿差异学习

不得只对 Agent 初稿和律师定稿做文字 diff。必须结合形成定稿的对话，还原“问题—建议—取舍—结果”。

### 必读内容

- 律师为什么提出该问题；
- Agent 当时给出的一般规则、法律边界和建议；
- 律师是否接受、收窄、扩张或拒绝该建议；
- 最终文本如何落地；
- 对话中是否已经说明取舍原因、适用范围或例外。

当前任务的对话已在上下文中时直接使用。历史对话无法读取时，先利用邮件、会议记录、审阅笔记、版本差异和客户反馈；只有缺失会实质影响长期知识时，才向律师提出 1—3 个针对性问题。

### 差异分类

| 差异 | 默认路由 |
|---|---|
| 客户事实或主体纠正 | 客户画像、发展历程或业务模式 |
| 真实业务流程、参与主体或权利来源纠正 | 业务模式或创新业务 |
| 法律关系、强制性边界或持续执行要求 | 法律边界 |
| 客户特定风险偏好或长期业务选择 | 客户画像或业务模式 |
| 本次谈判妥协、金额期限或个案选择 | 仅在重要事项页保留，不自动晋升 |
| 律师的通用审查方法或写作偏好 | 用户级 `AGENTS.md` 或对应法律 Skill，不写入客户画像 |
| 纯文字、风格或排版修改 | 不编译 |

“采用了”不当然等于长期规则；“没有采用”也不当然等于以后禁止。只有对话、定稿和业务上下文共同支持时，才提炼为可复用知识。

## 四、知识晋升门槛

先问：本次定稿是否改变、强化或限定了上述四类长期认知？

符合以下任一情形时才晋升：

- 会改变后续法律判断、合同结构或业务执行；
- 属于该客户特有的主体、产品、流程、管理或风险安排；
- 涉及创新业务或多方参与的复合法律关系；
- 未来不得静默背离的法律边界或执行要求；
- 重新推导成本较高，需要同时还原多份文件、对话或取舍；
- 在两个以上事项中重复出现并已形成稳定处理方式。

普通物业、租赁、采购、服务等简单法律关系，如无客户特殊事实、新的法律边界或高复用价值，不深编；必要时只在日志或原材料地图记录定稿位置。

## 五、法律边界与冲突处理

法律边界页应写明：

- 已确认边界；
- 适用的业务、主体和触发条件；
- 定稿和对话中的取舍理由；
- 例外或不适用场景；
- 对应定稿、对话或已核验依据；
- 确认时间和后续变更记录。

新任务与已编译边界看似冲突时，不得静默产生相反结论。必须先判断：

1. 是否因本次事实、主体、用途或风险不同而可以区分；
2. 是否因现行法、监管口径或新证据变化；
3. 是否律师明确改变了旧口径。

可区分的，在新页或原页补充适用边界；旧口径确已变更的，更新当前口径并在时间线、事项页和日志中保留历史。

## 六、状态和更新

进入长期 Wiki 的知识默认已经律师确认，不为 Agent 初稿建立“待确认知识”，也不设置“依据未核验草案”等知识状态。律师定稿已发出，确认的是律师的审查立场和法律判断；Agent 初稿仅用于与律师定稿比较，对话仅用于还原提问、建议和最终取舍。

根据项目需要使用简洁状态：

```yaml
knowledge_status: 律师已确认
delivery_status: 律师定稿已发出 | 客户反馈后已更新 | 签署或执行材料已复核
confirmed_content: 审查立场和法律判断 | 客户事实 | 执行状态
confirmed_at: YYYY-MM-DD
sources:
  lawyer_final: 律师定稿路径
  agent_draft: Agent 初稿路径，仅用于差异比较
  decision_dialogue: 对话记录位置，用于还原取舍
  other_evidence:
    - 客户反馈、签署稿、执行材料或已核验依据
```

对同一事项的后续反馈，优先更新现有页面和时间线，不因版本每变一次就新建重复知识页。历史定稿文件和旧结论不删除，但当前口径必须明确。

## 七、新项目初始化

### 先读项目上下文

1. 读取当前目录及上级的 `AGENTS.md`；
2. 检查客户目录、已有定稿、邮件、会议记录和项目说明；
3. 判断客户的主要发展线、业务模式、创新业务和高风险法律边界；
4. 不因目录中存在大量普通合同而默认全量编译。

### 建立精简结构

```text
wiki/
  规则.md
  索引.md
  日志.md
  原材料地图.md
  客户画像/
    公司发展历程.md
    主体与产品.md
  业务模式/
  创新业务/
  法律边界/
  事项/
```

只在客户实际需要时新建合同类型、条款口径、监管司法观点、风险跟踪或办案方法目录，不把它们作为每个项目的强制骨架。

### 生成项目级入口

项目级 `AGENTS.md` 仅增加类似以下的简短入口：

```markdown
## 客户 Wiki

本项目同步编译客户级 Wiki。每次处理客户事项时，先完整读取 `wiki/规则.md`，再按其路由读取 `wiki/索引.md` 和相关页面。完整编译规则只维护在 `wiki/规则.md`，不在本文件重复。
```

如 `AGENTS.md` 已有项目规则，只追加或替换 Wiki 入口段，不覆盖其他规则。

### 冷启动

1. 先建立原材料地图和定稿候选清单；
2. 优先找律师定稿、客户反馈和签署或执行材料；
3. 对能获取的对话、邮件、审阅说明和版本差异还原律师取舍；
4. 只编译会改变后续处理的高价值客户认知；
5. 先向律师报告候选晋升项，再按确认范围深编。

## 八、成熟项目的移交边界

项目完成初始化并建立自己的`wiki/规则.md`后，日常增量编译即移交给项目规则。本 Skill 不重复规定其触发条件、经验显化问题、页面路由、状态字段、写入闭环或交付提示，也不因用户说“编译 Wiki”而当然介入成熟项目。

仅在下列情形重新使用本 Skill：

1. 项目尚未建立 Wiki 或需要历史材料冷启动；
2. 项目规则、目录结构、知识晋升标准或冲突机制需要升级；
3. 需要跨多个事项批量补录、重构长期认知或审计来源与冲突；
4. 用户明确指定使用`legal-client-wiki`。

成熟项目的单事项增量编译，应完整执行其`wiki/规则.md`，但不再加载本 Skill 的通用方法。

## 九、查询和复用

回答或修订新事项时：

1. 先从索引定位客户发展、业务模式、创新业务和法律边界；
2. 必要时追溯定稿、对话取舍和历史事项；
3. 已编译边界可作为当前办案起点，但涉及法律变化、新业务、对外正式引用或新证据时仍应核验；
4. 不得跨客户将一家公司的事实、偏好或妥协直接用于另一家公司。

## 十、质量门槛

每次编译后检查：

- 是否只使用律师已确认定稿或后续确认事实；
- 是否读取了定稿形成过程中可获取的对话；
- 是否分清事实纠正、法律取舍、商务妥协和文字调整；
- 是否说明可复用结论的适用范围和例外；
- 是否对与旧边界的冲突作出区分或更新；
- 是否避免编译普通简单事项和无长期价值内容；
- 是否将律师通用方法留在用户级规则或法律 Skill，而非客户画像；
- 是否更新索引、日志和原材料地图；
- 是否保留客户原始材料和历史定稿。

## 输出边界

本 Skill 产出内部客户认知，不替代对外法律意见、合同修订稿、尽调报告或客户答复。不因编译 Wiki 移动、删除或覆盖客户原始文件。
